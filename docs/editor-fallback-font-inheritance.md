# 日本語の後に挿入した記号が代替フォントで細く描かれる問題

編集画面で箇条書きを書いていると、日本語を含む項目の行末で Return を押した以降の行だけ、行頭のハイフンが約半分の長さになり、ハイフンと本文の間隔も狭くなった。右側のプレビューと保存される本文には影響がない。表示だけの問題である。

## 再現条件

既定のフォント設定（システム等幅、13pt）で次のように入力する。

1. `- 1` と入力して Return を押す。自動で `- ` が続く。同じ操作で `- 2`、`- 3` も入力する。
2. 4行目の `- ` の後に日本語（例: `あ`）を入力して確定し、Return を押す。
3. 5行目以降に自動で挿入された `- ` は細く描かれる。4行目までのハイフンは正しい幅のまま残る。

切り替わるのは日本語を入力した行の次の行からである。日本語を入力した時点で既存のハイフンが変わるわけではない。日本語を含む行の行末で Return を押すと、次の行の `- ` が細くなる。同じ原因で、日本語だけを選んで太字にしたときの `**` も細くなる。

ファイルの再読み込みなどで編集画面の外から本文が変わったときは、文書の先頭の文字が日本語だと、置き換えた全文の英数字と記号が代替フォントで描かれる。

## 原因

`NSTextStorage` はレイアウトのときに属性を補正し（`fixAttributes(in:)`）、本文フォントにない文字には表示できるフォントを割り当てる。既定の本文フォント（SF Mono）は日本語を含まないため、日本語の文字の `.font` 属性はヒラギノ（`.HiraKakuInterface-W4`）に書き換わる。

キー入力（`insertText`）は、テキストビューの入力属性（`typingAttributes`）で文字を挿入する。プレーンテキストの `NSTextView` では入力属性が本文フォントに保たれるため、日本語の直後でも英数字は SF Mono で入る。

一方、リストの自動継続などの編集コマンドは、`MarkdownEditorModel.perform` で `NSTextStorage.replaceCharacters(in:with: String)` を直接呼んでいた。文字列で置き換えると、新しい文字は置換範囲の先頭の文字（範囲が空なら直前の文字）の属性を引き継ぐ。日本語の直後に `\n- ` を挿入すると、ハイフンと空白は直前の日本語のヒラギノを引き継ぐ。ヒラギノでは13ptのハイフンの幅が約4.5pt、空白が約4.0ptで、SF Mono の約8.0ptの約半分になる。日本語を選んで太字にした場合は、置換範囲の先頭が日本語なので `**` がヒラギノになる。

`updateNSView` の `textView.string = text` も全範囲の置き換えなので、先頭の文字の属性を全文が引き継ぐ。

この経路は2026-09-28の編集コマンドの共通化（`12c6f0d`）からある。エディタの配色（`ec377e2`、`b7181cd`）は文字色と一時属性だけを変更しており、この問題とは関係しない。

## 修正

`MarkdownTextEditor.swift` の `NSTextView` の拡張に、置換文字に付ける属性を決める関数を2つ追加した。どちらも `NSAttributedString` で置き換え、記号には本文フォントを付ける。日本語には、レイアウトのときの補正で改めて代替フォントが付く。

- `replaceEditorCharacters(in:with:)`（編集コマンドの2つの `perform` が使う）: 文字列で置き換えたときと同じく、置換範囲の先頭の文字（範囲が空なら直前の文字）の属性を引き継ぐ。そのうえで、フォントを入力属性のフォント（本文フォント）に替え、段落スタイルを挿入先の段落の先頭の文字のものにする。本文が空のときは引き継ぐ文字がないので、キー入力と同じく入力属性を付ける。
- `replaceEditorText(with:)`（`updateNSView` の外部変更の反映が使う）: 本文フォントと文字色だけを付ける。開いたとき（`makeNSView` の `textView.string = text` の後に `textView.font` と `textView.textColor` を設定する経路）と同じ属性になる。

本文フォントには `textView.font` ではなく入力属性の `.font` を使う。プレーンテキストの `NSTextView` の入力属性は、日本語の後でも本文フォントのままである。一方 `textView.font` は先頭の文字のフォントを返すので、先頭が日本語の文書ではヒラギノになる。入力属性は IME の変換中（マーク付きテキストがある間）に代替フォントになることがある。呼び出し元はすべて `hasMarkedText()` が偽であることを確認してから置き換える。

修正前に細く描かれた記号は、本文フォントの設定を変える（文字サイズを変えるなど）か、文書を開き直すと正しい幅に戻る。`textView.font` の設定が全文のフォントを置き直すためである。

### 入力属性を丸ごと付けない理由

最初の修正では、置換文字に入力属性（`typingAttributes`）を丸ごと付けていた。レビューで、フォント以外の入力属性まで置換文字に広がると指摘され、次のことを確かめた。

- 段落の書字方向は、標準のキー割り当て ⌃⌘←（`makeBaseWritingDirectionRightToLeft:`）で変えられる。プレーンテキストのこの編集画面でも、キャレットのある段落だけが右から左・右揃えになり、入力属性の段落スタイルも右から左になる。⌥⌃⌘←（`makeTextWritingDirectionRightToLeft:`）は、選択範囲がなければ入力属性にだけ文字方向（`.writingDirection`）を入れる。テキストビューの標準のコンテキストメニューにある「文章の方向」は、この環境の編集画面のメニューには出なかった。
- プレーンテキストの `NSTextView` では、キャレットを別の段落へ動かしても入力属性は更新されない。いったん右から左にすると、入力属性はその後も右から左のまま残る。
- 段落スタイルは、段落の先頭の文字のものが段落全体に使われる（`fixAttributes(in:)` の段落スタイルの補正）。置換文字が段落の先頭に入ると、その文字の段落スタイルが段落全体に使われる。

このため入力属性を丸ごと付けると、段落の先頭から始まる範囲を書式変更したときにその段落が右から左になり、外部変更を反映したときには全段落が右から左になった。文字方向も、書式変更の記号と反映した全文に付いた。

また、開いたときの本文には段落スタイルが付いていない。入力属性の段落スタイル（行間3pt）を付けると、外部変更を反映した後だけ行の高さが16ptから19ptに変わった。

この編集画面の本文と入力属性に付く属性は、通常はフォント、文字色、段落スタイルで、上の操作をすると文字方向が加わる。フォントと文字色は `textView.font` と `textView.textColor` の設定で全文にそろう。段落スタイルと文字方向は、上の操作で段落や文字ごとに変わる。字句の色とスペルチェックの印は一時属性（`NSLayoutManager` の temporary attributes）なので本文には入らない。リンク（`.link`）は、コンテキストメニューの「自動置換」で「スマートリンク」を有効にすると、検出したURLに付く。フォントパネルなどから付ける文字の属性（下線、カーニングなど）が全文にそろうかは確かめていない。プレーンテキストでは `rangeForUserCharacterAttributeChange` も `rangeForUserParagraphAttributeChange` も全文を返したが、段落の書字方向の操作は1段落だけを変えた。

そこで、全文に同じ値が付く文字色などは元の文字から引き継ぎ、代替フォントを引き継がないようにフォントだけを置き換え、段落スタイルは挿入先の段落のものにした。外部変更の反映では、元の段落と新しい全文の段落が対応しないので、開いたときと同じ属性にした。元の文字からリンクを引き継ぐ動作は、修正前の `replaceCharacters(in:with: String)` から変えていない。

### 残っている問題

開いたときの本文に段落スタイルが付かないため、環境設定の行間は、開いた後に入力した段落にしか効かない。`EditorTextStyle.apply(to:)` も `defaultParagraphStyle` と入力属性だけを変えるので、行間やタブ幅を変えても既存の本文には反映されない。この問題は今回の修正の範囲外である。直すときは、開いたときと外部変更の反映（`replaceEditorText(with:)`）の両方で同じ段落スタイルを付ける。

## 検証

- `EditorCommandFontTests` は、編集画面と同じ設定のプレーンテキストの `EditorTextView` で `setMarkedText` と `insertText` による日本語入力を再現し、レイアウトで代替フォントが付いたことを前提として確認してから、次を検査する。修正前はすべて失敗する。
  - 日本語の行の後で Return を押して続けた `- ` が本文フォントで、1行目の `- ` と同じ幅になる。修正前は約8.5ptと約16.1ptだった。
  - 日本語の選択範囲を太字にしたとき、単一選択と複数選択の両方で `**` が本文フォントになる。
  - `NSHostingView` に載せた `MarkdownTextEditor` で、先頭が日本語の文書の本文を外から変えたとき、英数字と記号が本文フォントになる。
- `EditorReplacementParagraphStyleTests` は、`doCommand(by:)` で ⌃⌘← と ⌥⌃⌘← の操作を再現し、段落と入力属性が右から左になったことを前提として確認してから、次を検査する。入力属性を丸ごと付けた実装では4件とも失敗する。
  - 別の段落の先頭から始まる選択範囲を太字にしても、その段落の段落スタイルが変わらない。
  - 段落の先頭に空の範囲で挿入した文字が、前の段落ではなく挿入先の段落の段落スタイルを持つ。段落スタイルを挿入先の段落から取る処理を外すと、この1件だけが失敗する。
  - `NSHostingView` に載せた `MarkdownTextEditor` で外部変更を反映した後、全段落の書字方向と揃えが既定（natural）のままで、1行目の高さが開いたときと同じになる。
  - 文字方向の入力属性が、書式変更の記号にも外部変更で反映した全文にも付かない。
- フォントを本文フォントに替える処理を外すと、`EditorCommandFontTests` の編集コマンドの3件が失敗する。
- 文字の属性を調べるときは、`layoutManager.ensureLayout(for:)` でレイアウトしてから `.font` を読む。レイアウト前は補正が済んでいないので、代替フォントが付いていない。
- テストで書字方向を変えるときは、キーイベントではなく `doCommand(by:)` を使う。テスト環境では `interpretKeyEvents` や `keyDown(with:)` に ⌃⌘← のイベントを渡しても、キー割り当てが働かなかった。
- 新しく `NSTextStorage` を直接書き換える処理を追加するときは、文字列ではなく、編集なら `replaceEditorCharacters(in:with:)`、全文の差し替えなら `replaceEditorText(with:)` を使う。
