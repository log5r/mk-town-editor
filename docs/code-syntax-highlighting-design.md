# コード色分けの設計評価

[現在の仕様](code-syntax-highlighting.md)に対する2026-10-09時点の調査。以下は提案であり、解析エンジンの変更はまだ実装していない。

追加調査として、[VS Code・CotEditor・Zed・Helixの構文着色方式](editor-syntax-highlighting-research.md)を比較した。CotEditor 7系はSwiftTreeSitterと従来の正規表現方式を併用しており、本提案に近い実例となる。TextMate方式も実用的な選択肢であり、構文解析の採用自体を目的とはしない。

## 評価

現在の「コード本文 → 範囲と字句の種類 → 表示先ごとの描画」という分離は維持する。`CodeSyntaxTokenRange` はFoundationだけに依存し、配色、原文への位置対応、HTMLのエスケープを解析から分離できている。未知の言語を単色にする方針、原文を改変しない方針、テーマのコントラスト試験も継続する。

一方、汎用スキャナーに言語固有の構文判定を追加し続ける方針は見直す。`CodeSyntaxTokenizer.swift` は1,442行あり、`regexAllowed`に加えて、関数・クラスの宣言と式の区別、JavaScriptの文の終端、Rubyの代入・引数・スコープを追跡している。これらは文字列の区切りやキーワード一覧という設定値では表せず、構文の一部を手書きで実装している。状態を一つ追加すると、改行、コメント、括弧、別の言語の規則との組み合わせを検証する必要が生じる。

したがって、問題は正規表現を使っていないことや、ファイルの行数自体にはない。多数の言語について構文上の判断を自前で保守していることにある。言語別ファイルへの分割は読みやすさを改善するが、この保守責任は減らさない。簡易な字句解析を続ける選択も成立するが、その場合は誤判定を仕様として受け入れ、構文の推定を拡張しない範囲を決める必要がある。

## 解析結果の共有

編集画面の色分けは `DocumentSnapshot` の生成中に計算され、`DocumentAnalysisStore` の通常の更新ではメインアクター外で処理される。ところが、プレビューの `CodeSyntaxHighlighter.render` は `@MainActor` 上で `CodeSyntaxTokenizer.tokens` を呼び直す。`PreviewRenderCache` は描画済みの結果を保持するものの、キャッシュにないブロックの解析はメインアクター上で行われる。HTML書き出しにも独立した解析呼び出しがある。

重いエンジンへの置き換え前に、コード本文に対する解析結果を共有できるようにする。現行資料にある25ミリ秒と150ミリ秒は既存実装の過去の測定値であり、今回の再測定結果でも、新エンジンの性能予測でもない。

## 候補の比較

| 方法 | 適する条件 | このアプリでの判断 |
| --- | --- | --- |
| 現行スキャナーの継続 | 依存を増やさず、色分けの対象を限定する | 構文推定の修正を続ける費用が残る |
| Tree-sitter + SwiftTreeSitter | ネイティブ画面で範囲を扱い、構文に基づく分類を行う | 第一候補。言語文法とクエリの導入・更新管理が必要 |
| Shiki / TextMate文法 | 既存の多言語文法とテーマを利用する | 有力な比較候補。JavaScript実行環境との接続、範囲と既存の字句種別への変換を要する |
| highlight.js | HTML中心の出力を短期間で実装する | 公開APIの主な結果がHTMLなので、AppKit向けの範囲への変換が別途必要 |

Tree-sitterは編集途中の構文エラーを含む入力を扱うことを目標とし、構文木へのクエリで色分けの種類を抽出する。[公式の概要](https://tree-sitter.github.io/tree-sitter/index.html)と[色分けの説明](https://tree-sitter.github.io/tree-sitter/3-syntax-highlighting.html)を参照。SwiftTreeSitterにはUTF-16を前提とした`NSRange`のアクセサーがあり、現在のAppKit側のデータ形式と接続しやすい。ただし、低水準のライブラリであり、言語パーサーは別途導入する。[SwiftTreeSitterの説明](https://github.com/tree-sitter/swift-tree-sitter)

ShikiはTextMate文法を利用し、HTML以外の中間表現も扱える。候補から外す理由を「HTMLしか返せない」とするのは誤りである。このアプリでは、Swiftへの接続費用と既存テーマを保つ変換処理を含めて比較する。[Shikiの概要](https://shiki.style/guide/)・[API](https://shiki.style/api)。highlight.jsの`highlight`は色分け済みHTMLを返すため、同じ範囲列を全表示先で使う構成には追加の変換が必要になる。[highlight.js API](https://highlightjs.readthedocs.io/en/latest/api.html)

Tree-sitterの採用で、各言語の仕様への完全準拠が保証されるわけではない。Rubyの曖昧な構文、方言、未完成の入力の扱いは、採用する文法の版とクエリに依存する。`eval`などの実行時状態は静的な解析の対象外とする。今回、代替エンジンを組み込んだ実測や誤判定の比較は行っていない。

## 推奨する構成

1. Markdown解析でコード本文と原文への位置対応を取得する。現行の引用・リスト内の対応付けをまず維持し、タブなどの変換に対応する際はMarkdown解析側で明示的な位置対応表を作る。
2. 言語名を解決し、本文を解析して`[CodeSyntaxTokenRange]`を生成する。外部ライブラリの型はこの境界から外へ出さない。
3. 範囲をUTF-16に統一し、本文の範囲内・位置順・非重複に正規化する。Tree-sitterの入れ子や重複するcaptureには優先順位を定める。現行HTML出力は非重複の範囲を前提としているため、この処理を省略できない。
4. 文書の同じ版に属する解析結果をスナップショットなどの不変データに保持する。編集画面は原文上の範囲へ変換し、プレビューは属性付き文字列を生成し、HTMLは原文をエスケープしてspanを付ける。PDF・印刷・コピーも対応する描画経路から同じ解析結果を使う。
5. 未対応の言語、解析の中断、範囲の検証失敗では単色表示に戻す。構文エラーがあるだけで全体を失敗扱いにせず、利用できる解析結果は使用する。

言語解決では、現在同じ字句規則にまとめている別名を点検する。たとえばTSとTSX、HTMLとXML・Vue、SQLの各方言は、導入するパーサーに応じて区別する必要がある。現在の別名表をそのまま新エンジンの言語IDに置き換えると、対応しているように見えて違う文法で処理する可能性がある。

解析はメインアクター外の専用ワーカーで行い、可変なパーサーを複数のタスクから同時に使わない。既存の世代番号による公開制御を維持し、古い文書版の結果で新しい原文を着色しない。巨大なブロックでは解析のキャンセルと処理量の制限を設ける。

まずはコードブロック全体の解析と、言語・本文・エンジン／文法／クエリの版に基づく容量制限付きキャッシュを実装する。色と原文上の絶対位置はキャッシュに含めず、テーマ変更やブロックの移動で再解析しない。最初から文書全体の差分解析を導入せず、計測して必要な場合に、変更したコードブロック内で構文木を再利用する。本文のハッシュを使う場合は同一性の確認も行う。

## 移行と検証

最初の比較対象はJavaScript・TypeScript・Rubyとする。既存の正規表現リテラルと除算の回帰例、および既知の制約の例を新旧両方に入力し、改善・維持・悪化を記録する。旧実装の色分けそのものを正解にはせず、各例の意図に基づいて評価する。JSX・TSX、文字列内の式、未完成の入力も比較に含める。

比較の結果が採用条件を満たせば、この3言語から切り替える。残りの言語は既存スキャナーで維持し、対応言語を落とさずに順次移行する。移行済みの言語の構文推定コードは削除する。Diffなどの単純な専用処理は、保守費用を比較して残してよい。

導入時には次を確認する。

- 日本語、絵文字、結合文字、CRLF、複数行の字句、引用・リスト内の範囲対応。
- captureの重複解決、範囲外アクセスの防止、未完成の文字列や括弧からの回復。
- 編集画面・プレビュー・HTML・PDFの分類の一致、原文の保存、エスケープ、既存テーマのコントラスト。
- キャッシュの言語／版の分離、本文変更時の無効化、文書版が変わった際の古い解析結果の破棄。
- 初回解析と再利用時の時間、入力から反映までの遅延、メインスレッドの占有、メモリ、配布サイズ。
- SwiftPMとXcodeの両ビルドへの組み込み、文法とクエリの互換性、バージョン固定、各依存物のライセンス。

現段階の推奨は、表示と配色の設計を保ち、解析結果の共有を導入したうえで、Tree-sitterを上記3言語で検証することである。全言語の一括置換は、その比較結果と配布サイズ・性能を確認してから判断する。

## 今回の確認結果

実装コードの呼び出し関係をレビューし、文書だけを追加・更新した。`swift test`は1,037件、`python3 -B -m unittest discover -s Tools -p 'test_*.py' -v`は27件が成功した。UIテストは実行していない。これらは現行実装の確認であり、提案するエンジンの品質や性能を検証した結果ではない。
