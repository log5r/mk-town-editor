# 全角文字の後に半角文字を入力すると本文が上下に動く問題（#113）

macOS版の編集画面で日本語だけの行に英数字を追加すると、その行の日本語の位置と行の高さが変わった（[issue #113](https://github.com/log5r/mk-town-editor/issues/113)）。保存される本文は変わらず、TextKitによる表示位置の問題である。

## 再現と原因

Menloを選び、`日本語`をIMEで入力・確定してから、同じ行の末尾に半角の`a`を入力すると再現した。文字サイズ13・17.5・26ptで、ベースラインと行の高さがそれぞれ1pt増えた。13pt、既定の行間3ptでは、行の先頭からベースラインまでの距離が11ptから12ptに、行の高さが19.5ptから20.5ptになった。同じ環境のシステム等幅とシステムフォントでは再現しなかった。代替フォントやメトリクスはOSとフォントに依存するため、この差をすべての環境の固定値として扱わない。

本文フォントに含まれない日本語には、`NSTextStorage`の属性補正で代替フォントが付く。日本語だけの行は代替フォントのメトリクスで配置されるが、半角文字を追加すると本文フォントも行のベースラインの計算に加わる。Menloのベースラインに必要な領域の方が大きいため、既存の日本語まで下へ動いた。半角文字を削除すると逆の移動が起こる。

代替フォントの割り当て自体は正常な動作である。[日本語の後に挿入した記号が代替フォントで細く描かれる問題](editor-fallback-font-inheritance.md)とは、同じ代替フォントが関係していても原因が異なる。今回は挿入した半角文字のフォントが正しくても、行全体の配置が変わっていた。

## 修正

`EditorTextView`の`NSLayoutManagerDelegate`で、行のベースラインが本文フォントの`defaultBaselineOffset(for:)`を下回るときだけ補正する。[Appleの行フラグメントの補正API](https://developer.apple.com/documentation/appkit/nslayoutmanagerdelegate/layoutmanager(_:shouldsetlinefragmentrect:linefragmentusedrect:baselineoffset:in:forglyphrange:))を使い、レイアウトが確定する前に次の3つを同じ差分だけ増やす。

- 行の先頭からベースラインまでの距離。
- 行全体の矩形の高さ。
- 行の使用領域の矩形の高さ。

日本語だけの時点から本文フォントのベースラインに必要な領域を確保するため、後から本文フォントの半角文字が加わっても位置が変わらない。矩形の高さも増やし、下側の文字領域を狭めない。TextKitがより大きいベースラインを提案したときは、その値を維持する。行高やベースラインを一律の固定値にはしない。

基準のフォントには、`EditorTextStyle.apply(to:)`が記録する`appliedBodyFont`を使う。`NSTextView.font`は先頭文字のフォントを返すため、先頭が日本語なら代替フォントになり得る。入力属性もIMEの変換中は代替フォントになることがあるため、基準に使わない。段落属性や保存する文字列には手を加えない。

この補正は本文フォントの半角文字を追加・削除したときの揺れを対象とする。異なる高さのフォントや文字を新たに含めた場合まで、すべての行の高さを同じにするものではない。

### 本文フォントは設定変更より先に記録する

`textView.font`や余白のセッターは、その場で同期レイアウトを起こすことがある。新しい本文フォントをセッターの後に記録すると、古い基準で補正された行がレイアウトのキャッシュに残る。後から半角文字を入力して再レイアウトしたときに新しい基準が使われ、再び位置が動く。

この経路は、レイアウト済みの日本語にフォントと文字サイズの変更を繰り返すテストで確認した。基準をセッターの後に記録する順序では、位置と行高の比較が18件失敗した。`didApplyTextStyle(_:font:)`を`prepareToApplyTextStyle(_:font:)`に改め、`EditorTextStyle.apply(to:)`のフォントと余白の変更より先に呼ぶことで、新しい基準を同期レイアウトにも使う。

## 関連する処理経路

macOS版の編集ビューは`MarkdownTextEditor.makeNSView`で作成し、既存のレイアウトマネージャーのデリゲートに`EditorTextView`を設定している。通常入力、IME、編集コマンド、外部変更による全文更新、Undo / Redoは、いずれもこの行レイアウトを通る。文字列の置き換え方法ごとに属性の補正を追加する必要はない。iOS版は別の`UITextView`実装であり、今回の変更はmacOS版に限る。

行番号・折りたたみマーカー、不可視文字、タイプライターのスクロール先、ソース位置へのスクロールは、TextKitの行やグリフの矩形を参照する。補正後の矩形に追従する。[行番号のY座標の揺れ](line-number-vertical-alignment.md)にある、行番号だけの中央揃えやプレビューのスクロール同期による問題とは区別する。

## 検証

`EditorTextStyleTests.testJapaneseBaselineStaysStableWhenTypingAndDeletingASCII`は、本番と同じデリゲートを設定したプレーンテキストの編集ビューで、次を確認する。

1. `setMarkedText`と`insertText`で、日本語の変換・確定を再現する。
2. `ensureLayout(for:)`で代替フォントの割り当てとレイアウトを確定する。
3. 半角の`a`を入力し、先頭の日本語グリフのベースラインと行高が変わらないことを確認する。
4. `a`を削除し、本文が`日本語`に戻り、ベースラインと行高も変わらないことを確認する。

標準装備の3種類のフォントと、インストール済みのヒラギノ・セリフ・等幅フォントでも検査する。文字サイズは13・17.5・26pt、行間は0・3・12ptとする。修正前のMenloでは追加時・削除時ともに失敗する。

同じテストクラスに、次の検査も追加している。

- `testWrappedJapaneseAndFollowingLinesKeepTheirPositionsAfterASCIIEdit`: 折り返す日本語の段落を外部更新と同じ全文置換の関数で設定し、末尾の表示行に半角文字を追加・削除しても、折り返し先と次の段落の位置が変わらないこと。
- `testChangingFontAndZoomOnLaidOutJapaneseKeepsBaselineStable`: レイアウト済みの本文のフォントと文字サイズを繰り返し変更した後も、半角文字の追加で位置が変わらないこと。
- `testTallFallbackGlyphsKeepTheirOriginalLineGeometry`: 本文フォントより大きいベースラインを必要とする絵文字を含む行で、補正なしのTextKitと同じ位置・高さが保たれること。

これらを含む`EditorTextStyleTests`と、フォントの解決・追加・削除を検査する`EditorFontSelectionTests`は、合計22件すべて成功した。

最終確認では、macOSサービスを利用できる環境で`swift test`を実行し、1,387件が成功、10件が既存の条件によりスキップ、失敗は0件だった。スキップはIcon Composer未導入による3件と、明示的に有効化する性能測定7件である。`Tools`のPythonユニットテストも109件すべて成功した。修正コードのレビューと、同じレイアウトを通る入力・更新・折りたたみの経路の確認も完了している。
