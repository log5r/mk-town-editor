# 文書内のテキスト検索・置換

macOS・iOS・iPadOSで、開いている書類の本文を検索・置換できる。対象はMarkdownの原文で、フロントマターやコードブロックも含む。

## 操作

| プラットフォーム | 検索・置換の開き方 |
| --- | --- |
| macOS | 「編集」の「検索…」（⌘F）または「置換…」（⌘⌥F） |
| iOS・iPadOS | ツールバーの虫眼鏡「検索・置換」、または外付けキーボードの⌘F。検索欄のメニューから置換へ切り替える |

検索欄に文字列を入力し、前後の一致へ移動する。置換欄には新しい文字列を入力し、1件ずつ置換するか、すべて置換する。空の置換文字列で一致箇所を削除できる。変更は通常の書類編集と同じ保存処理に反映され、Undoで取り消せる。

iOS・iPadOSでは、検索中に本文の下部にも現在位置と総数を表示する。検索バー内の件数をOSが非表示にした場合も、この専用欄で確認できる。

iOS・iPadOSでプレビューだけを表示している場合、検索を開くと編集画面へ切り替わる。検索を閉じても本文は編集画面に表示する。プレビューに切り替えると検索UIを閉じる。

macOS版では、一致箇所の一覧や正規表現での検索、[フォルダ全体の検索・置換](features.md#文書内の移動と検索)も使える。

## macOSの一致箇所一覧

「編集」→「文書内検索・置換…」を選び、検索欄に文字列を入力する。未保存の書類でも、一致した箇所の行番号と前後のテキストが一覧に表示される。矢印キーで項目を選び、Returnまたはクリックで原文の位置へ移動する。検索対象を選択範囲に絞ったり、文末と文頭の間で検索を折り返すかを選んだりできる。

通常検索では、文字の幅、ひらがなとカタカナ、アクセント記号の違いを個別に無視できる。たとえば幅を区別しない設定では `ABC` で `ＡＢＣ` にも一致する。単語単位で一致させる設定もある。正規表現を使う場合は、同じ画面で切り替えるか、「編集」→「正規表現検索・置換…」（⌘⇧F）を選ぶ。正規表現ではパターンのメタ文字と置換欄のキャプチャ参照が色分けされる。

「すべてハイライト」を押すと、一致箇所を本文上で強調できる。強調表示は検索画面を閉じた後も残る。解除するには、検索画面の「ハイライトを解除」か、「編集」→「検索の強調表示を解除」を選ぶ。本文を変更したときも強調表示が消える。検索語と置換文字列は、それぞれの履歴から再利用できる。履歴はこのMacに保存され、各履歴メニューから消去できる。

## 標準UIを使う設計

標準検索には、macOSでは既存の`NSTextView`と`NSTextFinder`、モバイル版では編集欄の`UITextView`が持つ`UIFindInteraction`を使う。OSが検索結果の表示・移動・置換・Undoを処理する。検索UIのラベルと検索オプションもOSが提供する。

macOSの一致箇所一覧は、検索に使う本文のスナップショットから、原文のUTF-16範囲、行番号、短い抜粋を背景処理で求める。検索条件や本文が変わったら古い計算を取り消し、その結果を表示や置換に使わない。本文上の強調表示は表示範囲に限って描画するため、文書全体の文字属性を書き換える必要がない。強調表示によって保存内容やUndo履歴は変化しない。

モバイル版の表示状態は`MobileEditorState`で管理する。検索要求時は編集欄を表示し、自動配置の設定は維持する。検索中に表示メニュー、画面幅、アクセシビリティの文字サイズ変更で編集欄が隠れた場合も、検索の表示状態を解除する。

新しく生成した編集欄へ同時に検索UIの表示を要求すると、編集欄だけが表示され、検索UIが開かない場合がある（`TextEditor`を使っていた時期に確認した）。`MobileFindNavigator`は要求を保留し、UIKitの入力欄と検索機能の準備を300ミリ秒待ってから表示する。`Task.yield()`だけでは準備前に再開する場合がある。画面を切り替えると待機タスクがキャンセルされるため、古い要求による再表示も防げる。

プレビュー専用の表示では編集欄を取り除き、フォーカスと検索の表示状態を解除する。幅0の編集欄を残す構成も検証したが、iPad上で検索セッションが終了せずに残る場合があった。編集欄が表示されたままの画面幅変更では、既存の入力欄を維持する。

## 検証

`FindReplaceCommandsTests`はmacOSの標準検索アクションと、入力変換中の一括置換の抑止を確認する。`MobileEditorLayoutTests`は各表示モード・画面幅・アクセシビリティ文字サイズからの検索開始と、プレビューへの切り替え後の検索再開を確認する。

macOSの拡張検索は、全角・半角、かな、結合文字、絵文字を含む本文で照合する。テストでは、一致範囲で原文を選択・置換できること、10万行の文書で行番号が正しいこと、履歴の保存とキャプチャ参照の色分けも確認する。

`MobileWorkspaceTests`は実際の編集欄で標準検索が有効になっていることを確認し、日本語・絵文字を含む検索、前後移動、1件置換、空文字列への一括置換、該当なし、Undo、保存後の再読み込みを検証する。

`testFindRequestPresentsNavigatorAfterLeavingPreview`は、プレビューから検索UIが開くことと、プレビューへ戻ると検索UIが閉じ、もう一度開けることを確認する。

検索UIを伴うテストでは、実際の書類画面と同じ`NavigationStack`とツールバー内に編集欄を配置し、`UIHostingController.viewDidAppear`を待ってから操作する。表示・終了の判定も固定時間の待機だけで済ませず、検索UIの表示状態とバインディングの更新を待つ。

テストが取り除かれた`UITextView`を参照している間は、検索セッションや表示状態のフラグが残る場合がある。取り除いた入力欄の`findInteraction`では終了を判定せず、バインディングと画面内の編集欄の有無、`editor.window == nil`を検証する。再表示時は新しい入力欄の`isFindNavigatorVisible`を確認する。

2026-10-27に最新mainを取り込んだ状態で全Swiftテスト1,187件、iPhone Duo（iOS 27.1）とiPad Pro 13インチ（iOS 26.0）のシミュレータ上で各42件、補助スクリプトの71件が成功した。検索・置換メニューへの切り替えと、プレビューから検索を開く操作もDevice Hubで確認した。

## 連続移動で候補数が消える問題

macOSで40件の一致を検索し、「次を検索」を連続して押すと、標準検索バーの候補数が消える問題を確認した。候補移動に伴う選択範囲や画面の更新では、本文が変わっていなくても、編集可否・スペルチェック・自動修正の設定をAppKitへ再代入していた。同じ値の再代入を省いたところ、通常文とインラインコードを交互に含む文章でも、前後各45回の移動と折り返し後に候補数が残ることを確認できた。

編集可否の更新は`updateEditorEditability`にまとめ、校正設定も現在値と異なる場合だけ更新する。設定を変更した場合や、コードと通常文の間で校正の有効・無効が変わる場合には、従来どおり新しい値を適用する。検索エンジンと検索バーはOS標準のまま使う。

⌘G・⌘⇧Gからの移動でも、検索欄から本文へフォーカスを移すことで候補数が消える経路があった。検索バーを表示中の前後移動では現在のフォーカスを維持する。検索バーを開いていない場合の移動や、検索・置換UIを開く操作では本文へフォーカスする。

`FindReplaceCommandsTests`は、繰り返し更新しても同じ設定のsetterを呼ばないこと、編集可否の変更を適用すること、検索バーの表示中に前後移動してもフォーカスを要求しないことを検証する。40件の一致を前後に選択する経路も検査する。コード内の校正抑止と通常文への復帰は、既存の`EditorSourceCacheTests`と`MarkdownProofingTests`で確認する。

iOS・iPadOSは`UITextView`とUIKitの検索機能を使い、macOSのAppKit設定処理を共有しない。`MobileWorkspaceTests.testFindCountSurvivesRepeatedNavigationAndViewUpdates`は日本語と絵文字を含む40件の一致を前後各85回移動し、現在位置・総数・検索UI・入力欄と検索セッションの継続・候補数ラベルの表示を検証する。各移動でSwiftUIの更新も要求し、本文が変わらないことを確認する。

検索UIの検証では、候補が実際に移動したことも確認する。macOSの非アクティブなテストウインドウでは、候補が動かず総数だけ読める場合がある。総数が残っているという検査だけでは連続移動の検証にならないため、macOSは設定更新のユニットテストと実アプリでの操作確認を組み合わせる。モバイルのテストでは、検索UIを開く前に`UIFindInteraction.searchText`も設定する。セッションの`performSearch`だけでは、検索欄と候補数ラベルを含む表示を検証できない。

2026-10-27の修正後は、次の環境で成功した。iOS・iPadOSの実行はシミュレータによる。

| 環境 | 確認結果 |
| --- | --- |
| macOS 27.0.1 | 全Swiftユニットテスト1,190件成功。実アプリでボタン・⌘G・⌘⇧Gの連続移動と折り返し後の候補数表示を確認 |
| iPhone Duo / iOS 27.1 | モバイルの全43テスト成功。40件の候補を前後各85回移動し、各移動後の候補数ラベルも検査 |
| iPad Pro 13インチ（M5）/ iPadOS 26.0 | モバイルの全43テスト成功。同じ連続移動・表示検査を実行 |
| iPhone 17 / iOS 26.0 | 連続移動・表示検査が成功。通常のiPhoneの画面幅でも確認 |

### iPhone Duo実機での追加調査

上記の検証後、iPhone Duo実機（iOS 27.1）の録画で別の表示問題を確認した。9件目までは件数が見え、10件目から消えていた。実機上で長い文章と実際の`MobileEditorWorkspace`を使って再現すると、検索結果と現在位置は正しいまま、UIKitの件数ラベルが`10 / 40`を保持して`isHidden == true`になることを確認できた。`UIFindInteraction.updateResultCount()`を呼んでも、この非表示は解除されなかった。

初回のモバイルテストは短い文章を簡易な`TextEditor`に表示していたため、実際のワークスペースで発生する件数表示の問題を検出できていなかった。追加の回帰テストでは本番のワークスペースを表示し、ツールバーから検索を開く。長い日本語の文章に40件の一致を用意し、標準の前後ボタンを各45回操作して、現在位置と総数が専用欄に表示されることを検査する。

修正では、標準検索バーの件数とは別に、本文下部へ件数専用の領域を設けた。公開APIの`UIFindSession.resultCount`と`highlightedResultIndex`を50ミリ秒間隔で読み、変化した場合だけラベルを更新する。検索・強調・前後移動・置換は引き続きOSが処理する。検索セッションや本文へ書き込む処理は追加しない。

専用欄は検索中だけ存在し、検索を閉じるか編集欄を取り除くと更新タスクをキャンセルする。文字は標準のキャプション書体とDynamic Typeを使い、VoiceOverにも件数を公開する。回帰テストは件数ラベルの実表示と幅、検索語を変更したときの該当なし・再検索、検索終了後のラベル除去と本文入力も確認する。

追加修正の検証は、利用者の希望によりシミュレーターで実施する。実機では修正前の再現まで確認しており、追加修正後の実機動作は未確認。

追加修正後は全Swiftユニットテスト1,190件を実行し、既存の5件がスキップ、失敗は0件だった。iPhone Duo（iOS 27.1）とiPad Pro 13インチ（iPadOS 26.0）のシミュレーターでは各44件が成功した。Duoの長文テストはアプリを起動し直して3回繰り返しても成功し、各移動後に専用ラベルの表示値が実際の現在位置・総数と一致することを確認した。通常のiPhone 17（iOS 26.0）シミュレーターでも同じ長文テストが成功した。

CIのPython設定検査は、ワークスペース内の`UIViewRepresentable`を一律に禁止していたため、件数ラベルの追加で失敗した。画面サイズ・端末種別への依存とセーフエリアの無視を禁じる検査は維持し、標準編集欄の利用は`TextEditor`と本文・選択範囲のバインディングを直接確認する。件数ラベルのUIKit接続自体をレイアウト違反とは扱わない。ローカルでCIを検証するときも、Swiftのテストだけでなく`Tools/ci.sh`のPython設定検査とReleaseビルドを含めて実行する。

### DuoをClosedにした場合の追加検証

初回の長文テストは390×700ポイントの固定領域を使い、DuoのClosed状態や検索中の開閉を確認していなかった。Device HubでClosedを選び、実際のウインドウ全体を使うと、専用件数欄が本文の途中に重なることを確認した。標準検索UIは内部のテキストビューの領域を変更するため、`TextEditor`への下部セーフエリア挿入だけでは本文と件数欄の描画領域を分離できなかった。

件数欄を`VStack`内の独立した行として編集欄の外へ配置し、編集欄の描画を割り当てられた領域でクリップする。検索中にUIKitのテキストビューが広がっても、件数欄へ本文がはみ出さない。回帰テストも固定サイズの親画面を取り除き、実際のウインドウ全体を使うように変更した。前後各45回の移動ごとに、件数欄が画面内に収まり、祖先ビューで欠けず、本文の可視領域と重ならないことを検査する。この検査は修正前のコードで失敗することを確認した。テストの文章と検索語は検証用の定型データだけを使う。

Device Hubで検索中にClosed→Open→Closedと切り替え、標準検索バー内の件数が消えた状態でも専用欄が本文の下に残ることを目視確認した。Closed状態でモバイル全44件が成功し、長文の回帰テストはアプリの再起動を伴う3回の反復でも成功した。Open状態でも同じ回帰テストが成功した。SwiftUIの件数欄は検索セッションより遅れて挿入されることがあるため、テストでは欄が表示されてから検査する。`Tools/ci.sh`のPython検査71件、全Swiftユニットテスト1,190件（既存の5件はスキップ）、Releaseビルドも失敗なく完了した。

iPad Pro 13インチ（iPadOS 26.0）でもモバイル全44件、iPhone 17（iOS 26.0）でも長文の回帰テストが成功した。Closed対応後の実機での確認は行っていない。

## 編集欄をUITextViewへ置き換えたときの変更

長い書類で入力のたびに本文が揺れる問題（[原因と検証](mobile-editor-scroll-jump.md)）を修正するため、モバイル版の編集欄をSwiftUIの`TextEditor`から、`UITextView`を包む`MobileMarkdownTextView`へ置き換えた。検索の表示には`findNavigator(isPresented:)`を使わず、`UITextView.isFindInteractionEnabled`を有効にして`findInteraction`を直接操作する。

- `MobileEditorState.showsFindNavigator`が`true`になると`presentFindNavigator(showingReplace: false)`を、`false`になると`dismissFindNavigator()`を呼ぶ。新しい編集欄への要求を300ミリ秒待ってから表示する`MobileFindNavigator`の処理は従来どおり。
- 利用者が検索バーを閉じた場合や、システムの操作で検索を開いた場合は、`UITextView`が受け取る`UIFindInteractionDelegate`の開始・終了通知から表示状態を更新する。`UITextView`のサブクラスで2つの通知を受け、UIKit側の実装を呼んだ後に状態を書き換える。システム側から検索を開く経路は自動テストしていない。
- 編集欄を取り除くときは、検索UIが残っていれば閉じる。表示状態とフォーカスの解除は従来どおりワークスペースが行う。
- 件数欄は従来どおり編集欄の外の独立した行に置く。編集欄は割り当てられた領域でクリップする。

`MobileWorkspaceTests.testClosingSystemFindNavigatorResetsPresentationState`は、検索バーを閉じる操作で表示状態が解除され、同じ入力欄でもう一度検索を開けることを2回繰り返して確認する。既存の検索・置換・Undo・件数欄のテストは、新しい編集欄でそのまま成功した。
