# 数式の文字の大きさとベースライン（issue #97）

## 症状

1. インライン数式で `\displaystyle` を指定しても（`$\displaystyle \frac{1}{k}$`）、`$$...$$` の数式ブロックより小さく描かれた。
2. `(1) 確率 $\displaystyle\frac{1}{k}$ で当選する…` のように背の高いインライン数式を置くと、分母が本文のベースラインに乗り、分子が行の上へ大きく飛び出した。`$\lim_{k\to\infty} P_k$` も、下付きの `k→∞` がベースラインに乗るため、式全体が本文より浮いて見えた。

## 原因

### 大きさ

数式ブロックは文字の大きさ21pt（表示用の書体）で描いていた。インライン数式は周りの文字の大きさ（プレビューの本文は15pt、HTMLは16pt）で描いていた。
`\displaystyle` はSwiftMathの書体（分数や `\sum` の組み方）を切り替えるだけで、文字の大きさは変えない。そのため、同じ式でもインライン数式は数式ブロックより小さかった。

### 崩れ

`MarkdownMathRenderer.attachment` は、すべての数式で添付の位置を `bounds.origin.y = -2` に固定していた。
数式がベースラインより下に出る深さ（分数の分母、`\lim` の下付き、添字など）を無視していたため、画像の下端がほぼ本文のベースラインに来て、式全体が持ち上がっていた。
HTMLも `vertical-align:middle` で置いていたため、同じく数式のベースラインが本文とそろわなかった。PDFはHTMLを読み込んで作るが、読み込みが `middle` を無視するため、画像の下端がベースラインに乗っていた。

## 修正

### 数式の文字の大きさは1つの規則で決める

すべての数式（インライン数式、先頭に `\displaystyle` を書いたインライン数式、`$$...$$` の数式ブロック）を、**置く場所の文字の大きさの1.2倍**で描く。`\displaystyle` は分数や極限の組み方（TeXの書体）だけを変え、文字の大きさは変えない。

| 箇所 | 内容 |
| --- | --- |
| `MarkdownMathRenderer.fontScale` | 1.2。数式の文字の大きさの、周りの文字に対する倍率 |
| `MarkdownMathRenderer.fontSize(surrounding:)` | `surrounding × fontScale`。数式の大きさはすべてこれで求める |
| `MarkdownRenderer.bodyFontSize` | プレビューの本文の大きさ（15pt）。本文・リスト・表などのフォントと、数式ブロックの大きさに使う |
| `MarkdownRenderer.inline` | インライン数式は、その文字列のフォント（`baseFont.pointSize`）の1.2倍。見出しや脚注は自分の文字に合わせる |
| `MarkdownRenderer`（数式ブロックの添付）・`MarkdownMathView` | 本文の大きさの1.2倍（18pt） |
| `MarkdownHTMLExporter.MathImage` | 本文の大きさ × 場所の倍率（`textScale`）× 1.2。数式ブロックは場所の倍率1 |

1.2倍にするのは、数式用の書体（Latin Modern Math）が同じ大きさの本文の文字より小さく見えるためで、KaTeXも同じ倍率を使う。
同じ段落の `$ax+b$`・`$\displaystyle ax+b$` と、続く `$$ax+b$$` は同じ大きさの文字で描かれる。`$\frac12$` と `$\displaystyle\frac12$` の違いは書体（分子・分母を一段小さくするかどうか）だけになる。

#### 以前の判断（`\displaystyle` を数式ブロックの21ptにする）をやめた理由

最初の修正では、先頭が `\displaystyle` のインライン数式を数式ブロックと同じ21ptで描き、ほかのインライン数式は本文と同じ15ptのままにした。アプリで確かめたところ、1つの行の中で `$\displaystyle ax+b$`（21pt）が `$ax+b$`（15pt）より明らかに大きく、大きさが混ざって読みにくいという指摘を受けた。そこで、`\displaystyle` によって文字の大きさを変える規則（`Formula.usesDisplaySize`、`displayFontSize`）を取り除き、すべての数式を周りの文字の1.2倍にそろえた。数式ブロックも21ptから18pt（本文15ptの1.2倍）に変わった。

### HTMLの数式の大きさ

本文の大きさ `B` はプリセットの `fontSize`（標準は16px）。数式の大きさは `B × 場所の倍率 × 1.2`。

| 場所 | 場所の倍率 | 根拠 |
| --- | --- | --- |
| 本文・リスト・表のセル・引用・コールアウト・定義リスト・図・数式ブロック | 1 | スタイルシートがこれらの文字の大きさを変えない |
| 見出し h1〜h6 | 2・1.5・1.17・1・0.83・0.67 | `MarkdownHTMLExporter.headingFontScales`。同じ値をスタイルシートの `h1`〜`h6` の `font-size` に書き出す |
| 脚注 | 0.9 | `footnoteFontScale`。スタイルシートの `.footnotes` の `font-size` と同じ値 |

- 標準のプリセットでは、本文のインライン数式も数式ブロックも19.2px。24pxのプリセットでは28.8px、見出し1の中では57.6px、脚注では25.92px。丸めない（画像の大きさは描いた後に整数へ切り上げる）。
- 見出しの大きさはブラウザの既定値と同じ値をスタイルシートに明示した。既定値のままだと、コールアウト（`aside`）の中の `h1` のようにブラウザが別の大きさを使い、数式の大きさと合わなくなるため。表紙（`.cover h1`）は `revert` でブラウザの既定値に戻し、見た目を変えない。表紙と目次には数式の画像を置かない。
- 大きさは `MathImage` が式と場所の倍率（`textScale`）から求める。集める `formulas(in:bodyFontSize:)` は区画の種類（見出しの段・脚注）から、埋め込む `inline(_:textScale:)` は描く要素から同じ倍率を渡す。同期・非同期のどちらの書き出しも同じ関数を使う。キーには数式ブロックかどうか（`style` が異なる）と大きさを含め、見出しと本文の同じ式は別の画像にする。キーが食い違うと数式が原文に戻るので、場所ごとに画像が見つかることをテストで確かめる。
- 大きさはプリセットだけから決まるため、プリセットを渡さない呼び出し（スライドのPDF、リッチテキストのコピー、公開、パッケージ）は標準の大きさで、渡す呼び出し（PDF、HTMLの書き出し）はそのプリセットの大きさで、集める時と埋め込む時がそろう。

### ベースライン

| 箇所 | 内容 |
| --- | --- |
| `MarkdownMathRenderer.render` | 画像と、画像の下端から数式のベースラインまでの高さ（`baseline`）を返す |
| `MarkdownMathRenderer.attachment` | `bounds.origin.y = -baseline`。数式のベースラインを本文のベースラインに合わせる |
| `MarkdownMathRenderer.htmlImage` | インライン数式は `vertical-align:-<baseline>px;max-width:none` |
| `MarkdownMathRenderer.alignImportedMathAttachments` | PDF（文書・スライド）で、HTMLから読み込んだ下げ幅を添付の位置に移す |

`MTMathUILabel` は、式の高さ（`ascent + descent`、文字の大きさの半分未満なら半分）を上下中央に置く。式を置いた位置（`MTDisplay.position`）は公開されていないため、同じ計算で求める。

```text
baseline = (画像の高さ - max(ascent + descent, fontSize / 2)) / 2 + descent
```

画像の大きさは整数に切り上げ、高さは `fontSize / 2` 以上にする。HTMLの `width`・`height`（整数）で画像が拡大縮小されず、`-` のような低い式が画像の下にはみ出さない。切り上げで空いた分も上の式に含まれるため、画像の中のベースラインと一致する。

### 行の高さ

TextKitの実測（macOS 27、本文15pt、`lineSpacing` 3）では、添付をベースラインより下げた分も行の高さに含まれた。

| 添付（`bounds`） | TextKit 1の行の高さ | ベースラインより下 | TextKit 2の行の高さ |
| --- | --- | --- | --- |
| 高さ14、y=-2 | 21（通常の行と同じ） | 6（字の深さ＋行間） | － |
| 高さ40、y=-2 | 44 | 6 | 41＋行間3 |
| 高さ40、y=-20 | 43 | 23（20＋行間3） | 40＋行間3 |
| 高さ40、y=-30 | 48 | 33（30＋行間3） | － |

ベースラインより上は「添付の上側と文字の高さの大きいほう」、下は「添付の下側と文字の深さの大きいほう」に行間を足した高さになる。前の行の行間（3pt）が数式の上の隙間になり、その行の行間が下の隙間になる。そのため、`NSLayoutManagerDelegate` で行を広げる処理は加えていない。数式を含む行だけが広がり、ほかの行の行間は変わらない。数式を本文の1.2倍（18pt）にしたため、`$ax+b$` のような低い式でも行がわずかに広がることがあるが、広がるのはその行だけで、前後の行には重ならない。
添付を含む `HoverLinkText` は幅いっぱいに描き、`sizeThatFits` でビュー自身の `layoutManager`（TextKit 1）を使って測る。文字だけの文字列を測る `HoverLinkTextMeasurer`、PDFの `NSTextView` もTextKit 1で、表示と測定は同じ規則で決まる。

### PDF

HTMLの読み込み（`NSAttributedString` のHTML読み込み）は `vertical-align:-Npx` を画像の文字の `NSBaselineOffset`（-N）に変える。ベースラインはそろうが、TextKitは下げる前の高さも行の上側に取り、行の上に深さ分の空きができた（21ptで描いていた当時の `\displaystyle\frac{1}{k}` の行で、59ptのところ73.72pt）。`alignImportedMathAttachments` は負の `NSBaselineOffset` を持つ添付を、同じ画像で `bounds.origin.y` に下げ幅を持つ添付に置き換え、プレビューと同じ置き方にする。`vertical-align` に負の長さを付けるのは数式の画像だけなので、ほかの画像は変わらない。読み込み結果の添付は `NSTextAttachmentCell` を持ち、`bounds` を設定しても行の高さに反映されないため、置き換える。

### HTMLの数式を縮めない

書き出しのスタイルシートには `img { max-width: 100%; height: auto; }` があり、数式の画像にも当たる。幅の狭い画面では、本文より広いインライン数式が縮む。`vertical-align` の下げ幅は元の大きさの値のままなので、縮んだ数式は本文のベースラインより下がる（WebKitで、高さ21pxの式が12.5pxに縮むことを確かめた）。

CSSでは、画像の `vertical-align` を描いた幅に比例させられない。PDF（HTMLの読み込み → `alignImportedMathAttachments`）はpxの `vertical-align` を下げ幅として読むため、包む要素やスクリプトで置き換えることもしない。そこで、インライン数式の画像には `style` 属性で `max-width:none` を付け、縮めない。`style` 属性はスタイルシートの `img` の規則より優先される（スタイルシートに `!important` はない）。`height: auto` は残るが、幅が `width` 属性のままなので高さも元のまま（`height` 属性と同じ）になる。KaTeX・MathJaxのインライン数式も縮まない。本文より広い式は、狭い画面では本文の幅からはみ出す。
数式ブロック（`display:block`）はそろえるベースラインがないため、従来どおり幅に合わせて縮む。

## Retinaの画面でぼやける（数式の画像の解像度）

### 症状

Retinaの画面のプレビューで、リストの `- 行内に表示する数式 $ax+b$` の数式が薄くぼやけて見え、次の行の `- display style の数式 $\displaystyle ax+b$` はくっきり濃く見えた。2つの式は同じ大きさで描いている。

### 原因（実測で確認）

`MarkdownMathRenderer.render` は、ウインドウに置いていない `MTMathUILabel` を `bitmapImageRepForCachingDisplay`・`cacheDisplay` で画素の画像にしていた。ウインドウがないため画像は1倍（`ax+b` は50×14ポイントに対して50×14画素）で、2倍の画面では引き伸ばして描かれる。

- 2つの式の画像は画素単位で同じだった（50×14画素、異なる画素0）。`\displaystyle` は `ax+b` の組み方を変えない。
- 実際のプレビューの文字列を2倍のビットマップに描くと、数式の左端は2行とも画素の途中にあった（321.28画素と332.55画素）。引き伸ばすときの補間が置く位置の端数で変わり、濃い画素（明るさ0.35未満）の数は182と168、最も濃い画素は0.17と0.15で、2行で濃さが異なった。どちらもぼやけていて、ずれ方の違いが濃さの差に見えていた。

### 修正

- プレビューの数式の画像は画素を持たず、描くたびに描く先の解像度で式を描く `NSImage`（`NSImage(size:flipped:drawingHandler:)`、`MathDrawing`）にした。大きさとベースラインは変わらない（`ax+b` は50×14ポイント、ベースライン1.501）。修正後は2倍のビットマップで濃い画素が349と271（端数の違いは残るが、どちらも輪郭がくっきりする）、最も濃い画素は2行とも0.15になった。
- 文字色は描くときの外観（文字列を描くビューの外観）で `labelColor` を解決する。式を黒で描いて不透明部分だけを `labelColor` で塗り直す（`MTMathListDisplay` の色の設定は公開されておらず、設定した時点で色が決まるため）。描いた結果を画像に残さない（`cacheMode = .never`）。修正前は、組版した時点のアプリの外観で色が決まって画像に焼き込まれ、プレビューの描画結果のキャッシュはテーマごとにしか作り直さないため、システムの外観を切り替えたり、背景の暗いテーマをライトモードで使ったりすると、数式だけ古い色のまま残っていた。今は描くたびに色が決まる。
- 組版結果は作った後に変えず、描くときは読むだけなので、どのスレッドから描いても安全（`@unchecked Sendable`）。
- 数式ブロックの構造化プレビュー（`MarkdownMathView`）はもともとビューとして描いており、変えていない。

### HTML・PDF

- HTMLに埋め込むPNGは3倍の画素で描く（`htmlPixelDensity`、`pngData(_:density:)`）。`width`・`height` と `vertical-align` はCSSのpxのまま変わらない。3倍にしたのは、Retinaの画面（2倍）に加えて印刷・PDF（約288dpi）でもぼやけないためで、数式の画像は余白が多くPNGの圧縮が効くため、ファイルはあまり増えない（`ax+b` を19.2pxで描いた場合、1倍723バイト・2倍882バイト・3倍982バイト、`\displaystyle\frac{1}{k}` は457・600・642バイト）。
- PNGには解像度の情報（216dpi）が入り、`NSImage(data:)` やHTMLの読み込みは元のポイントの大きさで読む。PDFでは、HTMLの読み込みが作る添付の枠（`cellSize()`）の大きさ（ポイント）で置き直し（`alignImportedMathAttachments`）、画像は3倍の画素を保つ。
- 文字色は従来どおり、書き出すときのアプリの外観で決める。ダークモードで書き出すと明るい色の数式になるのは従来と同じで、今回は変えていない。
- リッチテキストのコピー、公開、パッケージ、一括書き出しはHTMLの書き出しを使い、`width`・`height` で大きさを決める。画素数がポイントと等しいことに頼る処理はない。

### 検証方法

`Tests/MKTownEditorTests/MarkdownMathResolutionTests.swift` で確認する。

- 数式の画像が画素の画像を持たず、大きさとベースラインが修正前と同じこと。2倍のビットマップに描いた結果が、1倍のPNGを2倍に引き伸ばした場合（修正前の描き方）より濃い画素を1.4倍以上多く持つこと。
- `$ax+b$` と `$\displaystyle ax+b$` の画像が同じに描かれること。ライトの外観では暗い色、ダークの外観では明るい色で描かれること。
- HTMLのPNGの画素数が `width`・`height` の3倍で、解像度の情報から求めた大きさが `width`・`height` と等しいこと。
- PDFの添付がポイントの大きさで置かれ、画像が3倍の画素を保つこと（ベースラインのテストもそのまま通る）。

同じように、ウインドウのないビューを画素の画像にしている箇所はほかになかった。プレビューの画像（`ImageResourceManager`）は最大960画素の縮小画像を作るが、これは写真の読み込みの負荷を抑えるための別の処理で、今回は変えていない。

## 設計上の判断

- 文字の書体（`labelMode`）は従来どおり `display` で決め、`MarkdownMathCompatibility.normalize` の書体の追跡は変えていない。先頭の `\displaystyle` は従来からSwiftMathの書体として効いている。
- プレビューの表示倍率（`PreviewTypography.scaled`）は文字だけを拡大し、数式の画像と `bounds` は変えない（従来どおり）。数式ブロックの `MarkdownMathView` も倍率によらず18ptのため、インライン数式と数式ブロックの大きさは倍率によらずそろう。ベースラインの下げ幅も画像の座標なので、倍率を変えてもずれない。数式が文字と一緒に拡大されないことは、この修正の範囲外として残した。

## 検証方法

`Tests/MKTownEditorTests/MarkdownMathBaselineTests.swift` で確認する。

- 大きさの規則（1.2倍）と、プレビューで同じ段落の `$ax+b$`・`$\displaystyle ax+b$`・`$$ax+b$$` の画像が同じ大きさ（本文15ptの1.2倍）であること。構造化プレビューの `MarkdownMathView` の大きさも同じであること。見出しの数式が見出しの文字の1.2倍であること。`$\displaystyle\frac{1}{k}$` と `$\frac{1}{k}$` が同じ文字の大きさで描かれ、書体の違いだけで高さが変わること。
- 添付の `bounds.origin.y` が `-baseline` に等しいこと。画像のピクセルから、`x` の下端がベースラインにあり、分数の横線がベースラインの0.1〜0.45em上（数式の軸）にあること。
- 実際の構造化プレビュー（`NSHostingView` の `MarkdownPreview`、倍率1と1.5）で、段落の途中の行に置いた分数が前後の行の文字に重ならず、数式のベースラインが同じ行の文字のベースラインと一致し、行とビューの高さが広がること。`HoverLinkTextMeasurer` の測定とビューのレイアウトの高さが一致すること。
- HTMLで、インライン数式の `vertical-align` が `-baseline`、`max-width:none` であること（数式ブロックには付かない）。同じ式の数式ブロック・インライン数式・`\displaystyle`・脚注の数式が、それぞれの置き方と大きさで出力されること。
- 幅200pxの `WKWebView` に書き出したHTMLを置き、本文より広いインライン数式が元の大きさのまま、画像の下端がベースラインより `baseline` だけ下にあること。数式ブロックは本文の幅に縮むこと。`max-width:none` を外すとこのテストは失敗する。
- 標準のプリセットで本文の数式がすべて19.2pxで、24pxのプリセットで28.8px、見出し1が2倍、脚注が0.9倍になること（同期・非同期）。見出しと本文の同じ式が別の大きさで出力されること。見出し1〜6、本文、表の見出しとセル、脚注、リスト（番号・タスク・入れ子）、引用、コールアウト、引用の中の見出し、定義リストで、数式が原文に戻らず、その場所の大きさで出力されること（16px・24px、同期・非同期）。
- PDFで、添付に `NSBaselineOffset` が残らず、数式のベースラインが本文とそろい、行の上に余分な空きがないこと。

```sh
swift test --filter MarkdownMath
swift test
```

見た目は、文書を `MarkdownRenderer.render` で描き、`NSTextView` に流し込んで白背景のPNGに書き出して比べた（一時テストで作成し、リポジトリには残していない）。
